# Whole-display drag on nightly 580

Kept frames of one drag run: every partial frame lay inside the two drag bursts, and the picture was whole 0.1–0.4 s
after each burst's end. With 1 Hz host references a moving window has no reference at its moment, so the old 51%
was mostly the check, not the stream. Since ba6df2f the gate leaves frames from a burst's first input until the next
whole frame out of the partial count and reports that time as settle.

What stays wrong is text. In a scroll run whose start sent no lossless refinement tiles, a still screen showed 43–45
cells of the bench (its text lines) more than 15 levels off from 0.8 s until the first scroll at 12 s, through a
sharpening frame (QP ≤ 20) every second; after each drag the same kind of cells stay 6–15 levels off (one over 15)
until the next. Starts that did send refinement tiles were exact. Blur keeps a cell's mean, so encoding loss was the first suspect (HEVC Main, 4:2:0). It is not:
experiments/textbench puts a bench-like picture through the same hardware encoder and no cell moves more than 1.8 levels
at any QP we use, even from the coarse first IDR. The viewer was showing something other than the host's screen in
those cells (stale or missing content), which the earlier starts' lossless tiles happened to cover. That is a
correctness bug to find before whole display can be the default.

# The wrong text cells, found (2026-11-02)

A still whole-display run with full-size bench crops showed the bench as the 1/8-size start picture, upscaled, for the
whole run, through every sharpening frame and a native keyframe. The video tile key took its rank from the controller's
rung (native after the probe) while the encoder was still at the tiny size, so the tiny frames claimed native quality and
the real native frames tied and lost. Fixed with the encoder's own size as the rank, and whole display rebuilding its
encoder at the probe's rung without waiting for a base stage. Details in HANDOFF.md.
